# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

WOM is a turn-based 2D military strategy game (human vs AI in v1). The game design lives in `idea.md` and the full technical specification in `docs/especificaciones.md` — both in Spanish. The user communicates in Spanish; respond, document, and write docstrings in Spanish. Code identifiers are in English.

**Stack (decided)**: Python 3.13 + pygame-ce, JSON for config and savegames, pytest, PyInstaller for distribution (Windows + Linux + macOS; PyInstaller can't cross-compile, so each build runs on its own OS — WSL2 or CI).

## Commands

The virtualenv is `.venv\` (already created, pygame-ce and pytest installed).

```powershell
.venv\Scripts\python.exe -m pytest tests -v          # run all tests
.venv\Scripts\python.exe -m pytest tests/test_x.py::test_name  # single test
.venv\Scripts\python.exe main.py                     # run the game (pygame window)
.venv\Scripts\python.exe main.py --headless --seed 42            # AI vs AI console game
.venv\Scripts\python.exe main.py --headless --debug-ai           # log AI decisions
.venv\Scripts\python.exe tools\gen_placeholders.py   # regenerate placeholder PNGs
.venv\Scripts\python.exe tools\screenshot_m2.py      # render a game frame to docs/screenshot_m2.png (no window)
.venv\Scripts\python.exe tools\screenshot_menu.py    # render the 3 menu views to docs/screenshot_menu_*.png
.venv\Scripts\python.exe tools\simulate.py --games 30            # AI balance simulation (--detail for per-game)
.venv\Scripts\python.exe tools\llm_client.py --provider ollama --model gemma3   # LLM joins a hosted MP game as a net client
```

Scripts in `tools/` need the project root on `PYTHONPATH` (`$env:PYTHONPATH='D:\dev\WOM'`); `main.py` and pytest do not. UI tests run headless via `SDL_VIDEODRIVER=dummy` (set inside the test files).

## Architecture

Strict three-layer separation — **`wom/core/` must never import pygame** (enforced by `tests/test_smoke.py::test_core_does_not_import_pygame`):

- `wom/core/` — pure game logic: map + random generator (`worldmap.py`, `mapgen.py`), armies (`army.py`), turn engine (`game.py`), auto-resolved battles (`battle.py`), victory conditions (`victory.py`), config loading (`config.py`). Runs headless for tests and mass AI-vs-AI simulation. The map generator paints coherent features over plains (mountain chains as directed walks, forest blobs grown from seeds, lakes, and a river with passable fords every few tiles) targeting `TERRAIN_TARGETS` proportions; connectivity is still flood-fill-verified with retries.
- `wom/ai/` — AI players. Same interface as a human player: `decide_orders(game) -> list[Order]`. The three difficulty levels share one codebase (an objective-scoring engine: capture/attack/defend/resupply/garrison, discounted by distance/horizon) and differ only in weights and capability flags from `data/config/ai.json` (`agrupa`, `coordina`, `evita_peligro`, `divide` are dificil-only; `fusiona` is medio+dificil). Two key additions keep the AI from abandoning forts and let it reorganize like a human: a **garrison** objective (`peso_guarnicion`) makes an army on its own frontier fort — enemy within `GARRISON_RADIUS` — value staying, and pulls a free army to an undefended frontier fort; and the AI emits the same **reorganization** orders the human does (but applied through the normal orders flow, not immediately): `MergeArmyOrder` consolidates two adjacent weak rear armies (`fusiona`), `SplitArmyOrder` leaves a garrison and detaches a mobile force from a big army on a frontier fort (`divide`). Each AI also gets a **personality** at game start (agresivo/estratega/moderado, defined in `ai.json` under `personalidades`), chosen deterministically from the seed by `choose_personality(seed, player_id, names)`: it does NOT change the level's skill (horizon/agrupa/coordina/evita_peligro), only modulates character by multiplying weights (`mult_agresividad`, `mult_peso_economia`, `mult_peso_defensa`, `mult_peso_guarnicion`, `mult_umbral_ataque`) and can toggle `fusiona`/`divide`. Balance is validated with `tools/simulate.py` (mass AI-vs-AI, alternating sides); keep dificil > medio > facil when touching AI params.
- `wom/ui/` — the only package allowed to import pygame. Produces the same `Order` objects as the AI. Army reorganization is the exception to the orders flow for the human (immediate, outside turn phases — the AI does the same reorganizations through `Merge/SplitArmyOrder` in the normal orders flow instead): Shift+click on two adjacent own armies opens a per-class transfer modal that starts at "Todo" (classic full merge) and calls `Game.transfer_troops`; the HUD "Dividir ejército" button (or D key) opens the same kind of modal and calls `Game.split_army` (new army spawns on a free adjacent tile with no army/fort/town, inherits XP/food, both halves keep ≥1 troop). Both modals are `TroopPicker` in `wom/ui/dialogs.py` (−/+ per class, ×10 with Shift, "Todo"/"Nada", caps at class availability and a global cap). The map view has a camera (`wom/ui/camera.py`, pure Python, unit-testable): mouse wheel zooms in discrete levels anchored at the cursor (level 0 always fits the whole map centered); when zoomed, moving the mouse to the window edges pans (`Camera.edge_pan`, called once per frame from `GameScreen.draw` with the full window as bounds, so the real right edge — not the map/HUD boundary — activates it) and middle-mouse drag grabs the map (view-only, works during animations too); the renderer caches scaled `Assets` per zoom level, clips drawing to visible tiles, and `GameScreen.draw` sets a surface clip on the map area so the zoomed map never paints over the HUD. Path drawing is a "hand-drawn" stroke: Chaikin-smoothed curve with an arrowhead at the destination (`wom/ui/pathline.py`, pure). While tracing a path, double-clicking the destination confirms the route and releases focus (same as clicking the army itself). End-of-turn movement is animated in three phases (march → battle clash → retreat): the core records each army's traversed tiles in `Game.last_moves`, battle pairs in `Game.last_clashes` and who retreated in `Game.last_retreats` (transient, like `last_battles`, not serialized) and `wom/ui/animation.py` (pure Python, no pygame — unit-testable) interpolates them — during the clash both sides lunge at each other with a flash at the contact point, and retreat steps animate only after the clash. The battle result is *revealed* only when the clash ends (`TurnAnimation.result_revealed`): until then combatants show their pre-battle troop counts and the renderer hides this turn's crosses (`hide_new_crosses`); `GameScreen.end_turn` snapshots armies pre-turn so dying armies animate before vanishing (they disappear when their clash ends). The same module computes the spawn-highlight rings that mark the player's initial army during the first seconds of a new game (turn 0 only; dismissed on selection or first end-of-turn). **F1 abre una ayuda visual rápida** (`wom/ui/help_overlay.py`, `HelpOverlay`): modal por encima de todo (incluidos los demás modales y la animación), que `GameScreen.handle_event` atiende antes que nada y dibuja al final de `draw`. Lee los datos en vivo (`game.classes`/`config`/`victory_mode`) — tabla de tropas con vel/atq/def + "brilla en"/"vence a" derivados de `bonus_terreno`/`bonus_vs`, leyenda de terreno con costos, sitios, modo de victoria activo y pasos de "por dónde empezar". Muestra los **sprites reales** (los mismos PNG del mapa) en vez de cuadros de color, cargados con `assets.load_scaled(name, size)` (helper que escala un sprite a un tamaño arbitrario, con el mismo fallback que `Assets`) y cacheados en el primer dibujo. ESC/F1/clic la cierran. Es la versión corta de la guía completa `docs/como_jugar.md`.
- `wom/ui/editor_screen.py` — **editor de mapas/escenarios** (v0.5.0): misma forma que `GameScreen` (`handle_event`/`draw`/`wants_menu`/`capturing_text`). Mantiene un `Game` interno como buffer de edición (mundo de pura pradera vía `Game.from_setup`) y **reutiliza `MapRenderer`** para el lienzo; tras pintar terreno llama `MapRenderer.refresh_terrain()` (recomputa el autotiling de agua en vivo — antes se calculaba una sola vez en `__init__`). La sidebar es una paleta: terreno (los 6 `Terrain`), sitios (fuerte/pueblo), tropas (ejército) y borrador, aplicados con el **dueño** activo (Neutral/J1/J2); más menú Nuevo (tamaño preset → lienzo en blanco), Guardar / Guardar como…, Cargar (`ListModal` sobre `list_maps`), Generar aleatorio (confirma; usa `generate_map`) y Volver. **Guardado estilo editor**: recuerda el archivo en edición (`current_path`) y su metadata (`doc_meta`/`doc_image`); "Guardar" sobreescribe ese `.wom` (o abre el formulario `SaveForm` —título/descripción/victoria/IA/imagen— la primera vez), "Guardar como…" crea uno nuevo (nombre derivado del título), Cargar pasa a editar ese archivo y Nuevo lo descarta; el sidebar muestra `Editando: <nombre>`. Clic de tropas sobre un ejército existente abre `TroopPicker` para editar su composición. Las operaciones de edición (`set_terrain`/`place_site`/`place_army`/`erase_tile`/`new_blank`) mutan el buffer y se testean headless.
- `wom/persistence/` — JSON savegames in `saves/` (`savegame.py`: `save_game`/`load_game`/`list_saves`/`save_info`; all take an optional `directory`, which tests use with `tmp_path`). A savegame stores `format_version`, timestamp and `Game.to_dict()` — including the RNG state and each player's `ai_level` — so a loaded game continues deterministically. Balance config is re-read from `data/config/` on load, never stored. User preferences (music) live in `settings.py` → `settings.json` at the project root (gitignored), saved on every change. **Mapas y escenarios compartibles** viven en `scenario.py` (v0.5.0; **must not import pygame**, in the smoke test; full design in `docs/escenarios.md`): un contenedor `.wom` = ZIP con `scenario.json` (el *setup inicial* — `WorldMap.to_dict()`, tropas sembradas como `army_specs`, jugadores y metadata: título/descripción/`victory_mode`/`ai_level`) + `image.png` opcional. NO es un savegame (no lleva RNG/turno): `build_game(doc)` → `Game.from_setup(world, players, army_specs, victory_mode)` arranca una partida nueva en turno 0. Mismo formato para las dos cosas, distinguidas por tener título o no: un **escenario** (con título; se juega con la IA/victoria que trae) y un **mapa** (sin título; se juega como partida nueva eligiendo IA/victoria). API: `save_scenario`/`load_scenario`/`scenario_info` (lee solo el JSON, sin extraer la imagen)/`list_maps`/`build_game` + el dataclass `ScenarioDoc`. La imagen viaja como bytes crudos (la UI los convierte a Surface). Carpetas: `BUNDLED_SCENARIOS_DIR = data/scenarios/` (distribuidos con el juego) y `MAPS_DIR = maps/` (lo que guarda el editor y comparte el usuario; gitignored).
- `wom/net/` — multiplayer (v0.4.0, human vs human over LAN; **must not import pygame**, in the smoke test). Full design in `docs/multiplayer.md`. Methodology: **deterministic lockstep with the host as authoritative fallback** — both clients run the same `Game.run_turn` on the same orders + seed; only orders travel each turn (plus the initial `Game.to_dict()` and `MatchRules`). `protocol.py` (message dataclasses + length-prefixed JSON framing, `FrameDecoder`), `transport.py` (TCP `Connection` with a reader thread + queue drained once per frame, `Server`, `connect`), `session.py` (handshake/lobby state machine → high-level events; `HostSession`/`ClientSession`), `orders_codec.py` (`Order ↔ dict`, incl. `TransferTroopsOrder`), `state_hash.py` (per-turn digest over `to_dict`), `config_fingerprint.py` (handshake balance check), `rules.py` (`MatchRules`), and `lockstep.py` (`NetGame`: combines both players' orders in a canonical order, runs the turn, exchanges hashes, detects divergence and resyncs via `StateSync` → `Game.load_state` in-place). UI: `wom/ui/multiplayer_screen.py` (menu "Multijugador" → hub/create/connect/lobby, emits `NetGameStart`) and `GameScreen(net=…)` (the AI is replaced by peer orders; human reorg is **deferred via orders** in net mode, not immediate; turn timer auto-submits; chat + connection indicators in the sidebar; save disabled). Determinism is the load-bearing invariant — verified turn-by-turn by `tests/test_net_lockstep.py`.
- `wom/llm/` — LLM-controlled player (**must not import pygame**, in the smoke test). Full design in `docs/llm.md`. An LLM plays WOM as a regular **net client** (not an MCP server: that would invert control and clash with the turn-based lockstep). `LLMPlayer.decide_orders(game) -> list[Order]` has the **same signature as `AIPlayer`**, so it's a drop-in (net rival, single-player AI, or local benchmark). Per turn it builds a textual board view (`observation.py`: ASCII map + entity lists, enemies shown only by position/total), asks the model for a JSON array of **high-level intentions** (`actions.py`: move/create/merge/split/transfer/wait — NOT raw paths; it computes routes with the core's Dijkstra and validates owner/adjacency/reachability, dropping invalid actions with a reason), and parses tolerantly (`agent.py`: handles fenced/prose-wrapped JSON, retries once, then passes the turn). Backends (`backend.py`, stdlib `urllib` only, no SDKs): `OpenAICompatible` covers **Ollama + LM Studio + OpenAI**; `Gemini`; `Anthropic` — chosen by `make_backend(BackendConfig)`, API key from env. The system prompt (`prompt.py`) is generated from the live config (classes, victory mode). Entry point `tools/llm_client.py` connects to a human-hosted game (Multijugador → Crear). The LLM's non-determinism stays **outside** the simulation — it only produces orders; both peers still run the same `run_turn`. Tests: `tests/test_llm.py` (units), `tests/test_llm_net.py` (full loopback game in sync).

Music (`wom/ui/music.py` + `music_overlay.py`): `MusicPlayer` builds a playlist from the settings folder (default `data/music`, mp3/ogg), starts on a random track, and advances via `MUSIC_END_EVENT`. The M key toggles a modal player overlay handled at the app-loop level (above any screen); the menu's Opciones mode configures it through the player's setters (each applies and persists immediately). Everything degrades to silent no-ops when the mixer or files are unavailable (headless tests fake `wom.ui.music.mixer`).

Key invariants:
- All randomness goes through the game's seeded `random.Random` (`Game.rng`) — battles and map generation must be deterministic given a seed (replays, tests).
- Game balance lives in `data/config/*.json` (unit classes, battle thresholds, AI weights), never hardcoded.
- Turn phases run in fixed order (see `core/game.py` docstring): orders → movement → battles → capture → production → recovery → victory check.
- Fort production accumulates in `Fort.reserve`; troops enter the map only via a voluntary `CreateArmyOrder` (or the initial spawn). Production order among a player's forts rotates by turn so captured forts also produce when food is scarce. An army parked on its own fort auto-resupplies from the reserve up to `max_army_size` (food refill costs player stock); an army parked on an own town refills food directly, without touching the stock. Capturing a fort destroys its reserve. Each player's cumulative losses are tracked in `Player.troops_lost` (serialized, shown in the HUD).
- Placeholder asset sizes are a contract with future final art: tiles 64×64, units 48×48, icons 32×32 (see `tools/gen_placeholders.py`). The script writes `_<name>.png` always (placeholder reference) and `<name>.png` only if missing — running it never overwrites installed final art. Water uses autotiling (`wom/ui/tiling.py`, pure): 15 shore variants covering all 16 coast combinations (`water_n/s/e/w`, corners `water_ne/nw/se/sw`, channels `water_ns/water_ew`, U-shapes `water_u_n/s/e/w` named by the open side, `water_single`), chosen per tile by which orthogonal neighbors are land. Bridges (`Terrain.BRIDGE_H/V`, passable) are built by mapgen after all water is painted and extend shore-to-shore — a bridge never ends in water; they count as water for shoreline purposes. For movement they are single-axis tunnels: `WorldMap.can_step` rejects lateral entry/exit (BRIDGE_H connects only east-west, BRIDGE_V only north-south) and `neighbors()` enforces it for pathfinding, retreats and the mapgen connectivity check.

## Roadmap status

All v1 milestones (M1–M6, defined in `docs/especificaciones.md` §8) are **done** and tested: core + headless (M1), playable pygame UI (M2), three validated AI levels (M3), menu + savegames (M4), gameplay/presentation polish — cover art menu, army merging, music, sound/video options (M5), and distributable builds (M6). `main.py` opens the menu (`wom/ui/menu_screen.py`); in-game saving via HUD button or G key, ESC asks for confirmation and returns to the menu. v1 explicitly excludes: tactical battle zoom. Post-v1 added multiplayer (v0.4.0) and the **map editor + scenarios** (v0.5.0).

Menu flows (v0.5.0, in `menu_screen.py` → consumed by `app.py`): the main menu added **"Escenarios"** (lista `.wom` con título → modo `scenario_intro` que muestra título/descripción/imagen y emite `ScenarioChoice` → `scenario_game` honra la IA/victoria del `.wom`) y **"Editor de mapas"** (acción `"editor"` → `EditorScreen`; el loop lo trata como pantalla propia, vuelve al menú con `wants_menu`). En "Nueva partida" hay un selector **Origen del mapa: aleatorio / archivo**: en "archivo" se elige un `.wom` (modo `pick_map`) y `NewGameChoice.map_path` hace que `new_game` use su terreno+tropas pero con los jugadores/victoria del menú ("Cargar mapa").

Builds: `pyinstaller wom.spec` produces `dist/wom/` (onedir, windowed exe). All resource paths go through `wom/paths.py`: read-only `data/` resolves into the bundle (`sys._MEIPASS`) when frozen, writable `saves/` + `settings.json` sit next to the executable. The executable icon comes from `data/assets/icon.ico` (Windows) or `icon.icns` (macOS), pre-generated from `icon.png` by `tools/gen_icon.py` (needs Pillow, dev-time only) so the build itself doesn't depend on Pillow; the spec selects the format per platform and falls back to the PNG. Linux exes don't embed an icon. `.github/workflows/build.yml` tests and builds Windows + Linux + macOS artifacts on `v*` tags or manually (PyInstaller can't cross-compile; each platform builds on its own runner — the macOS one is `macos-latest`, arm64/Apple Silicon only).

Battle semantics: combat triggers when an army tries to *enter* an enemy's tile — armies never share a tile; each side fights from its own tile (own terrain bonus, defender gets fort/town bonus). Attacker classes with `ignora_bonus_fort` in `classes.json` (the arquero) cancel the defender's fort bonus for their own contribution — they fight the fort's garrison 1:1. Losers/retreaters fall back one tile, except an army standing on a fort: it never retreats (retreat only happens in open field), so a fort holder must be destroyed to dislodge it.

Site flags are owner-colored: `flag_red.png` (player 0), `flag_blue.png` (player 1), `flag.png` (gray, neutral); the mapping lives in `theme.flag_icon(owner)`.

The menu draws over `data/assets/title.png` (cover art with a central parchment scroll); the scroll's usable area is `SCROLL_AREA` in `menu_screen.py` as image fractions — keep them in sync if the art changes. Without the asset the menu falls back to the flat background.
